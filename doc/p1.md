## 一、整体架构理解

这个项目是一个 **Rust 实现的高性能撮合引擎核心库**，采用经典的 LMAX 架构模式。核心控制流如下：

```
命令输入 → [WAL 写入] → Disruptor/直接调用 → Pipeline
                                                  │
                                    ┌──────────────┼──────────────┐
                                    ▼              ▼              ▼
                               Risk R1      Matching Engine    Risk R2
                              (资金冻结)      (撮合成交)      (结算退款)
                                    │              │              │
                                    └──────────────┼──────────────┘
                                                   ▼
                                            ResultConsumer
```

**关键设计原则**：
- **确定性**：相同输入序列产生相同输出（单线程、无随机）
- **公平性**：价格优先 > 时间优先（FIFO）
- **可审计**：所有状态可通过 WAL 重放恢复
- **关注点分离**：撮合引擎不计算余额，风控引擎不做撮合

## 二、复刻路线图（分 6 个阶段）

### 阶段 1：数据模型层（1-2 天）

先定义核心类型，这是整个系统的骨架：

**必须定义的类型**：

| 类型 | 作用 | 对应源码 |
|------|------|----------|
| `OrderCommand` | 系统唯一输入载体，包含订单属性 + 处理结果 + 事件列表 | `src/api/commands.rs` |
| `MatcherTradeEvent` | 撮合输出事件（Trade/Reject/Reduce） | `src/api/events.rs` |
| `OrderAction` | Ask / Bid | `src/api/types.rs` |
| `OrderType` | GTC / IOC / FOK 等 | `src/api/types.rs` |
| `CommandResultCode` | 各阶段执行结果码 | `src/api/types.rs` |
| `CoreSymbolSpecification` | 交易对规格（币种、手续费、倍率） | `src/api/types.rs` |
| `L2MarketData` | 行情深度数据 | `src/api/market_data.rs` |

**核心设计决策**：`OrderCommand` 同时承载输入、过程状态和输出——命令在 Pipeline 中被逐步修改（`result_code` 和 `matcher_events`），最终传给 ResultConsumer。这是 LMAX 模式的特点：**一个对象贯穿整个流水线**，避免分配新对象。

### 阶段 2：订单簿实现（3-5 天，核心难点）

**推荐从 `NaiveOrderBook` 开始**（最易理解），然后升级到 `DirectOrderBook`（生产级）。

#### 2.1 OrderBook Trait 接口

```rust
pub trait OrderBook: Send {
    fn new_order(&mut self, cmd: &mut OrderCommand) -> CommandResultCode;
    fn cancel_order(&mut self, cmd: &mut OrderCommand) -> CommandResultCode;
    fn move_order(&mut self, cmd: &mut OrderCommand) -> CommandResultCode;
    fn reduce_order(&mut self, cmd: &mut OrderCommand) -> CommandResultCode;
    fn get_l2_data(&self, depth: usize) -> L2MarketData;
    fn get_symbol_spec(&self) -> &CoreSymbolSpecification;
    fn serialize_state(&self) -> OrderBookState;
}
```

#### 2.2 NaiveOrderBook（入门版）

数据结构简单清晰：
- `BTreeMap<Price, OrdersBucket>` — 价格有序的桶，每个桶内 `SmallVec<[Order; 8]>` 存订单
- `AHashMap<OrderId, (Price, OrderAction)>` — 订单快速查找

撮合流程：
1. 按价格顺序遍历对手方桶
2. 桶内按插入顺序遍历（FIFO）
3. 逐笔生成 `MatcherTradeEvent::Trade`
4. 未成交部分根据订单类型决定挂单（GTC）或拒绝（IOC）

#### 2.3 DirectOrderBook（生产默认版）

**这是你应该重点复刻的版本**，数据结构更精细：

- `Slab<DirectOrder>` — 订单竞技场分配（避免频繁 malloc）
- `Slab<Bucket>` — 价格桶竞技场分配
- `BTreeMap<Price, BucketIdx>` — 价格→桶索引映射
- `AHashMap<OrderId, OrderIdx>` — 订单ID→索引映射
- **双向链表**：同一价格桶内的订单通过 `next`/`prev` 链接；跨桶的最优订单通过 `best_ask_order`/`best_bid_order` 直接访问

撮合算法（`try_match`）：
1. 从 `best_ask_order`（对于买单）或 `best_bid_order`（对于卖单）开始
2. 检查价格是否可成交
3. `trade_size = min(剩余量, maker剩余量)`
4. 更新 maker 的 `filled`，更新桶 `volume`
5. 生成 Trade 事件
6. 若 maker 完全成交：移除订单，可能移除空桶
7. 沿链表 `prev` 方向推进到下一个 maker
8. 更新 `best_ask_order`/`best_bid_order`

**关键性能优化**：
- Slab 竞技场分配 → 无碎片、O(1) 分配/释放
- BTreeMap 价格索引 → O(log n) 价格查找
- 链表 best 指针 → O(1) 获取最优价格

### 阶段 3：风控引擎（1-2 天）

两阶段风控模型：

**R1 Pre-process（下单前）**：
- `AddUser` → 创建用户账户
- `BalanceAdjustment` → 充值/提现
- `PlaceOrder` → 资金冻结检查：
  - 买单冻结：`size × (reserve_price 或 price) × quote_scale_k + taker_fee × size`
  - 卖单冻结：`size × base_scale_k`
  - 余额不足 → `RiskNsf`，充足 → `ValidForMatchingEngine`

**R2 Post-process（撮合后）**：
- 遍历 `matcher_events`：
  - `Trade` → 买方返还差价 + 发放 base 币；卖方发放 quote 币 - 手续费
  - `Reject` → 返还冻结金额
- 设置 `result_code = Success`

用户账户模型（`UserProfileService`）：
- `AHashMap<UserId, UserProfile>`
- `UserProfile` 内含 `AHashMap<Currency, i64>` 余额表

### 阶段 4：Pipeline 流水线（1 天）

Pipeline 串联各处理器，执行顺序固定：

```rust
fn handle_event(&mut self, cmd: &mut OrderCommand) {
    // 1. 所有 Risk Engine 分片执行 pre_process
    for re in &mut self.risk_engines { re.pre_process(cmd); }
    // 2. 所有 Matching Engine 分片执行 process_order
    for me in &mut self.matching_engines { me.process_order(cmd); }
    // 3. 所有 Risk Engine 分片执行 post_process
    for re in &mut self.risk_engines { re.post_process(cmd); }
    // 4. 结果回调
    if let Some(consumer) = &self.result_consumer { consumer(cmd); }
}
```

**分片机制**：
- 风控按 `uid & (num_shards - 1)` 分片
- 撮合按 `symbol & (num_shards - 1)` 分片
- `num_shards` 必须为 2 的幂

### 阶段 5：持久化（1-2 天）

**WAL（Write-Ahead Log）**：
- 格式：`[4字节长度][rkyv序列化payload]`，追加写入
- 写入时机：`submit_command` 进入 Pipeline 前
- 重放：顺序读出并依次执行

**Snapshot（快照）**：
- `bincode` 序列化完整 `ExchangeState`（包含所有订单簿、用户状态）
- 文件名：`snapshot_{seq_id}.bin`
- 恢复流程：加载最新快照 → 从对应 WAL 位置重放后续命令

### 阶段 6：并发 Disruptor 接入（1-2 天）

使用 Rust 的 `disruptor` crate 实现无锁环形缓冲区：
- `ExchangeCore::startup()` 将 Pipeline 移入 disruptor handler
- 提交命令写入 ring buffer，handler 异步消费
- 处理结果通过 `ResultConsumer` 回调获取（不是通过 `submit_command` 返回值）

## 三、关键复刻建议

### 必须注意的设计陷阱

1. **Disruptor 模式下 `submit_command` 的返回值不含 `matcher_events`**——必须通过 `ResultConsumer` 获取结果
2. **风控不主动解冻**——完全依赖 `matcher_events` 中的 Reject 事件触发退款；如果撮合引擎出错未生成事件，资金会卡住
3. **`DirectOrderBookOptimized` 的状态无法被快照持久化**——`serialize_state` 返回空的 `DirectOrderBook`

### 当前项目未实现但规划中的功能

| 功能 | 状态 | 建议 |
|------|------|------|
| STP（自我交易预防） | 未实现 | 在撮合 `try_match` 中，成交前检查 maker_uid == taker_uid |
| Market Order | 未实现 | 语义上 = IOC + 价格保护（最大滑点） |
| tick size / step size / min notional 校验 | 未实现 | 在 R1 阶段增加合约规格检查 |
| `AdvancedOrderBook` 的流水线集成 | 未集成 | `add_symbol` 写死了 `DirectOrderBook`，需改为可配置 |

### 推荐的实现优先级

```
Phase 1: 类型定义 + NaiveOrderBook + 基础撮合（GTC/IOC）
         → 验证：能跑通一笔买卖撮合

Phase 2: 风控引擎（冻结 + 结算） + Pipeline 串联
         → 验证：完整的下单→冻结→撮合→结算链路

Phase 3: 升级到 DirectOrderBook（Slab + 链表）
         → 验证：benchmark 对比 NaiveOrderBook

Phase 4: WAL + Snapshot 持久化
         → 验证：宕机恢复后状态一致

Phase 5: Disruptor 并发 + 分片
         → 验证：load_test 百万级 TPS

Phase 6: 高级订单类型（PostOnly/FOK/Stop/Iceberg）
         → 可选：从 AdvancedOrderBook 移植
```
